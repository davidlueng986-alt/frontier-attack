## The negative result matters more

The obvious method — truncate `L(s) = Σ a_n n^{-s}` at 20,000 terms and fit the
slope at `s = 1` — **returns 0 for curves of rank 1 and rank 3**. It is not a
tuning problem. The partial sums oscillate with the cutoff:

```
11a1, N_cut = 10k/20k/50k/100k:  0.2754, 0.2095, 0.2252, 0.2675
37a1, N_cut = 10k/20k/50k/100k: -0.0508, 0.0658, -0.0511, -0.0241
```

At `s = 1` the Dirichlet series converges conditionally, so a sharp cutoff
converges to a cutoff-dependent offset, not to `L(1)`. Twenty thousand is
neither sufficient nor special.

The fix is the smoothed approximate functional equation (same `a_n`, same
brute-force point counts, no PARI/Sage). It is exponentially convergent and
recovers all four ranks exactly.

## What this does and does not unblock

**Does:** `plan/bsd.md` said the analytic side had no backend. It now has one,
and it is fast enough to sweep.

**Does not:** the output is a numerical order, not a certified one. There is no
interval bound, so it cannot yet be the `k` in the terminal object. A search
using it can produce `COUNTEREXAMPLE_CANDIDATE` and never `COUNTEREXAMPLE`.

Also unresolved: the conductor `N` is supplied from LMFDB. There is no Tate
algorithm, so the estimator cannot be pointed at a curve that is not already in
a database.

## Consequence for the plan

The BSD branch is now: `NO_ADMISSIBLE_ACTION` for a counterexample (unchanged —
the object has never existed and LMFDB covers everything below 500,000), but
the **coverage** action is feasible: sweep `N > 500,000` with `k ≤ 3` and flag
`r1 == r2 != k`.

That is still a coverage claim, not a solution. The difference is that it is now
a claim we can actually compute.
